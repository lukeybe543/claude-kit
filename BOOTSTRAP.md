# Using claude-kit as a Template

This guide explains how to bootstrap new projects with claude-kit's templates, hooks, and docs system.

## Quick Start

claude-kit doesn't need to live anywhere permanent. `install.py` and
`adopt.py` **copy** files into `~/.claude/` and into your project — once
they've run, nothing points back at the checkout you ran them from. Clone it
wherever's convenient, run the two scripts, delete the clone:

```bash
git clone --depth 1 https://github.com/lukeybe543/claude-kit /tmp/claude-kit
/tmp/claude-kit/bootstrap.sh /path/to/new/project
rm -rf /tmp/claude-kit
```

`bootstrap.sh` is just `install.py` (writes `~/.claude/hooks`, `~/.claude/skills`,
`~/.claude/agents`, `~/.claude/CLAUDE.md` — once per machine, idempotent) then
`adopt.py <project>` (scaffolds the project's docs — create-only, idempotent)
run back to back. To update later, re-clone (or keep a checkout anywhere and
`git pull` it) and run the same two scripts again.

If you'd rather keep a permanent local checkout to track your own edits to
claude-kit itself (see "Sharing Changes Back," below), that's fine too —
`~/.claude/claude-kit` is a reasonable spot, but it's a convenience, not a
requirement. Nothing about how hooks or skills work depends on where the
checkout lives.

## What the Bootstrap Does

`bootstrap.sh` (via `install.py` then `adopt.py`) sets up:

### 1. `.claude/` Directory (in the project, real files)
```
.claude/
├── notify.json       # Project-specific hook configs (merged with global)
├── settings.json     # Project-specific permission baseline
└── commands/
    └── check.md      # Template for your project's verification script
```

### 2. Master Docs (root level, the source of truth)
```
design.md    # Architecture — what's being built and why. Settled shape only;
              # anything still being tested/debated goes in decisions.md instead.
plan.md      # Sequencing — milestones, current status, what's next
README.md    # Outside summary, derived FROM design.md — never accumulates
              # its own architecture
```

### 3. Derived Docs (`docs/`, distilled from the master docs)
```
docs/
├── charter.md       # How to read the decision register
├── decisions.md     # Your project's decision log (one row per decision)
└── glossary.md      # Project vocabulary & terminology
```
`NEXT.md` is also derived (from design.md + plan.md) but isn't scaffolded —
it's generated by the `focus` skill once there's something to distil.

### 4. Project CLAUDE.md
A stub that references the global rules and fills in project-specific info —
**only** what's specific to this project, never a restatement of global rules:
- A pointer to design.md/plan.md/README.md (not a copy of their content)
- How to verify changes
- Environment gotchas
- Key decisions already made (the quick-reference list, not the mechanism)

## Your Workflow

### Machine Setup (once per machine)

```bash
# Any location works -- install.py copies into ~/.claude and doesn't care
# where the checkout lives afterward.
git clone --depth 1 https://github.com/lukeybe543/claude-kit /tmp/claude-kit
python3 /tmp/claude-kit/install.py

# Update any time: re-clone and re-run, or keep the checkout and git pull it.
```

This gives every project access to:
- **Hooks**: notification sounds, lint-on-edit, verification
- **Skills**: /charter, /decisions, /glossary, and 7 others
- **Agents**: reviewer, scout

### New Project

```bash
bootstrap.sh /path/to/myproject   # or: python3 adopt.py /path/to/myproject
                                    # (bootstrap.sh also runs install.py first)
cd /path/to/myproject
git init
# Fill in design.md and plan.md first — everything else derives from them
# Fill in docs templates or run /charter
# Point .claude/commands/check.md at your project's test/lint commands
```

Nothing to merge here — the target is empty, so every file is freshly created.

### Existing Project (like before94)

An existing project already has real content — design.md, plan.md, its own
CLAUDE.md. This is a **migration**, not a fresh scaffold, so `adopt.py` /
`bootstrap.sh` behave differently: they only ever *create* a file that's
missing, never overwrite one that exists. If a file exists and differs from
the template, you get a SKIPPED line with a diff command — merge by hand.

The actual migration work, in order:

1. **Run `install.py`** if the project still carries its own in-repo `.claude/`
   copy of the hooks (as before94 does) — this moves notify.py etc. to the
   machine-global location so the project stops shipping its own copy.
2. **Diff the project's CLAUDE.md against `global/CLAUDE.md`.** Anything that
   matches — the behavioural rules, the review-marks table — is leakage:
   delete it from the project file, since the global install now covers it.
   What's left should be *only* what's genuinely project-specific (see the
   before94 example worked through in this conversation).
3. **Run `adopt.py`** to fill in whatever's actually missing (commonly
   `docs/charter.md` / `decisions.md` / `glossary.md`, or `.claude/settings.json`)
   without touching design.md/plan.md/README.md, which already have real
   content.
4. **Don't rewrite design.md/plan.md to match the template's section
   headings.** The template shape is a starting point for new projects, not
   a schema existing docs must conform to — reshape only if the sections
   genuinely help, and treat any such reorg as a `REORG:` review, not a
   silent rewrite.

## Sharing Changes Back to claude-kit

This is the one workflow where a throwaway clone doesn't fit — you need a
checkout with its own git history to commit and push from. Keep one
somewhere durable (`~/.claude/claude-kit` is fine) instead of `/tmp`.

After improving a hook, skill, or template while working in a project:

```bash
# e.g. you tuned .claude/notify.json's verify command in before94 and want
# that as the new project-template default:
cp before94/.claude/notify.json ~/.claude/claude-kit/project-template/.claude/
git -C ~/.claude/claude-kit commit -am "Tune default verify command"
git -C ~/.claude/claude-kit push
```

A project should no longer carry its own copy of `hooks/` or `skills/` once
migrated (see "Existing Project," above) — the global `~/.claude/hooks` /
`~/.claude/skills`, updated by re-running `install.py`, is the only copy.

## CLAUDE.md at Multiple Levels

Three levels, each with a distinct job — don't create more than this:

```
~/.claude/CLAUDE.md              Machine-global. Behavioural rules that apply
                                  to every project, every phase. Rarely edited.
<project>/CLAUDE.md              This project only. A pointer to design.md/
                                  plan.md, plus what's genuinely local.
<project>/<subfolder>/CLAUDE.md  A specific part of the project. Claude Code
                                  discovers these automatically when you're
                                  working on files under that folder.
```

That third level is the right place for "particular parts of the project"
guidance — e.g. before94 could put Ansible-specific gotchas in
`ansible/CLAUDE.md` instead of the project root, since they're only relevant
there. No special setup needed; Claude Code loads any `CLAUDE.md` in the
directory tree above the files you're touching.

**What this deliberately doesn't have:** a CLAUDE.md that swaps by project
*phase* (architecture vs. implementation). Behavioural rules don't really
change between phases — what changes is how settled a given claim is, and
that's exactly what `docs/decisions.md`'s Band column already encodes
(`revisitable`/`mixed` during exploration, `firm` once tested and settled).
A second global file to toggle would scatter the one thing you said you
wanted centralised. If a phase distinction is worth stating, put one line in
the project's own CLAUDE.md ("currently in architecture/exploration — expect
`revisitable` bands, don't treat unbanded design.md prose as settled") rather
than swapping files.

## Project-Specific Hooks

Create `.claude/notify.json` to configure behavior for just this project:

```json
{
  "lint": ["python3", "{python}", "-m", "mypy", "{file}"],
  "lint_suffixes": [".py"],
  "verify": ["pytest", "-q"],
  "guarded_paths": ["setup.py", "pyproject.toml"],
  "guarded_text": ["VERSION = "]
}
```

Keys:
- **lint** — Run on each file written (exit non-zero refuses the write)
- **lint_suffixes** — Which files to lint
- **verify** — Full check before commits (runs on code change)
- **guarded_paths** — First edit prompts for permission
- **guarded_text** — Edit containing this text prompts for permission

## Hearing Notifications from Headless Boxes

If you develop on a remote droplet but sit at a workstation:

1. On your workstation, run install.py with `--desktop`:
   ```bash
   python3 ~/.claude/claude-kit/install.py --desktop
   ```

2. On the droplet, create `~/.claude/hooks/notify.local.json`:
   ```json
   {
     "local": "http://<workstation-tailnet-ip>:19191"
   }
   ```

Events will play on your speakers over the network.

## Troubleshooting

### Hooks don't fire in a new project
Hooks are wired into `~/.claude/settings.json` by `install.py`, with an
absolute path to `~/.claude/hooks/notify.py` baked in — nothing project-side
to configure. Hook config is cached for a session's lifetime; there is no
mid-session reload, and `/hooks` is read-only — it does not trigger one
either. **Restart the Claude Code session** after running `install.py` for
the first time or after settings change.

### A project file already exists and differs from the template
`adopt.py` (and `bootstrap.sh`, which calls it) never overwrites — it prints
a SKIPPED line with a diff command instead:

```bash
diff /path/to/project/CLAUDE.md /path/to/claude-kit-checkout/project-template/CLAUDE.md
```

Merge by hand, keeping what the project actually needs.
